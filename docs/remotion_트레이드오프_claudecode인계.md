# 모션랩 Remotion 파이프라인 — 트레이드오프 문서 (Claude Code 인계용)

*목적: 1차 설계 문서(`remotion_파이프라인_1차설계.md`)에서 나온 결정을 실제 구현 결정으로 확정한다. Claude Code가 이 문서를 읽고 바로 스캐폴딩·구현에 들어갈 수 있도록, 항목별로 "왜 이렇게 정했는지"와 "무엇이 아직 열려 있는지"를 구분해 둔다.*

---

## 사용 지침 (Claude Code가 이 문서를 읽을 때)

- **상태: 확정(Fixed)** 항목은 재논의하지 않고 그대로 구현한다.
- **상태: 오픈(Open)** 항목은 구현을 시작하기 전에 사용자에게 먼저 확인한다. 다만 각 항목에 "미확인 시 기본값"을 명시해 두었으니, 진행이 급하면 기본값으로 가정하고 그 사실을 사용자에게 명확히 알린 뒤 진행해도 된다.
- 항목 번호는 1차 설계 문서의 단계 번호(①~⑦)와 대응한다.
- **항목 15는 보안 규칙이다. 예외 없이 준수한다.**

## 상세 트레이드오프

### 1. 1차 최적화 포맷 — 쇼츠 vs 롱폼 vs 동시
| 옵션 | 장점 | 단점 |
|---|---|---|
| 쇼츠 먼저 | 제작 사이클 짧아 파이프라인 학습 속도↑, 실패 비용 낮음 | 롱폼 파생 시 레이아웃 재작업 필요 |
| 롱폼 먼저 | 본편과 톤 유사, 정보량 많은 콘텐츠에 적합 | 사이클이 길어 파이프라인 반복 학습이 느림 |
| 동시 설계 | 처음부터 두 포맷 다 대응 | 구현 복잡도 급증, 1차 목표(파이프라인 학습)에 방해 |

**확정**: 쇼츠 먼저. 이유는 사용자가 명시(2026-08-15 답변)했고, 프로젝트 1차 목표가 "파이프라인 자체를 구축·학습"이므로 사이클이 짧은 쪽이 유리.

**Claude Code 구현 영향**: 씬 컴포넌트는 처음부터 `width/height`를 props로 받도록 설계해 롱폼 파생 시 레이아웃만 분기 가능하게 한다. 로직(씬 순서, 오디오 동기화)은 포맷 독립적으로 유지.

---

### 2. 나레이션 방식 — AI TTS vs 자막만 vs 육성
**확정**: AI TTS. 사용자 명시. 완전 자동화가 1차 목표와 부합.

**Claude Code 구현 영향**: TTS API 호출 → 오디오 파일 저장 → duration 측정까지 하나의 스크립트(`generate-narration.ts` 등)로 파이프라인화할 것.

---

### 3. 씬 길이 동기화 — 오디오 기준 자동 계산 vs 고정 프레임
| 옵션 | 장점 | 단점 |
|---|---|---|
| 오디오 실측 길이 기준 | 나레이션과 화면이 항상 자연스럽게 맞음, 대본 수정 시 자동 반영 | TTS 생성이 선행되어야 컴포지션 duration이 확정됨 (렌더링 파이프라인 순서 제약) |
| 고정 프레임(수동 지정) | 스크립트 단계에서 바로 렌더 가능 | 나레이션 길이와 어긋나면 수작업 보정 필요 — 자동화 취지에 반함 |

**확정**: 오디오 실측 길이 기준. 자동화 파이프라인의 핵심 전제이므로 고정.

**Claude Code 구현 영향**: 파이프라인 실행 순서는 반드시 `script.json 생성 → TTS 생성/duration 측정 → script.json에 duration 역주입 → Remotion 렌더`가 되어야 한다. 이 순서를 깨는 최적화(예: 병렬화)는 하지 말 것.

---

### 4. 비주얼 제작 방식 — 코드 기반 모션그래픽 vs AI 이미지 vs 실사
| 옵션 | 장점 | 단점 |
|---|---|---|
| 코드 기반 모션그래픽 | Remotion 네이티브, 렌더 속도 빠름, 스타일 일관성 확보 쉬움, 추가 API 비용 없음 | 표현력이 이미지/영상보다 제한적 |
| AI 이미지 생성 | 표현력 높음, 다양한 비주얼 가능 | 생성 API 비용·시간, 스타일 일관성 관리 부담 |
| 실사 AI 영상 | 신기술 실험 가치 높음 | 파이프라인 복잡도·비용 가장 높음, 안정화 전 도입 시 리스크 |

**확정**: 1차는 코드 기반 모션그래픽. 프로젝트 지침상 "신기술 실험은 자유롭게, 단 파이프라인 학습이 우선"이므로, 파이프라인이 안정화된 후 AI 이미지/실사를 별도 실험 트랙으로 붙인다.

**진행 중인 논의 (2026-08-16)**: 002 v3 리뷰 이후 이미지 컷 4종 문법(실물 풀블리드/펀치인/빅넘버/다이어그램)이 제안됨. 실물 캡처 확보 방식은 항목 15의 보안 규칙을 따른다. 상세는 `claude/002_test_리뷰_개선백로그.md` 참조.

---

### 5. 자막 타이밍 — TTS duration 재사용 vs STT 강제정렬
**확정**: TTS duration 재사용 (STT 불필요). 나레이션 텍스트를 이미 알고 있으므로 문장 단위 duration만으로 충분. 단어 단위 정밀 싱크가 필요해지면 그때 Whisper 등 강제정렬 도입.

**Claude Code 구현 영향**: 1차 구현에 Whisper/STT 의존성을 추가하지 않는다. 자막 컴포넌트는 `script.json`의 `subtitle.text`와 씬 duration만으로 타이밍을 계산.

---

### 6. TTS 벤더 — ElevenLabs vs OpenAI TTS vs Azure TTS  **[오픈]**
| 옵션 | 장점 | 단점 |
|---|---|---|
| ElevenLabs | 한국어 품질·감정표현 우수 | 비용 상대적으로 높음 |
| OpenAI TTS | API 통합 쉬움(이미 Claude/OpenAI 생태계와 친화), 저렴 | 한국어 자연스러움 검증 필요 |
| Azure TTS | 한국어 보이스 선택지 많음, 기업 무료 티어 존재 | 설정 복잡도(Azure 계정/리소스 구성) |

**미확인 시 기본값**: ElevenLabs (품질 우선, 1차 목표가 학습/기록이므로 결과물 품질이 낮으면 콘텐츠 자체의 설득력이 떨어짐).

**Claude Code 구현 영향**: TTS 연동 모듈은 벤더 교체가 쉽도록 인터페이스를 분리해서 구현할 것(`ttsProvider.generate(text) → { audioPath, durationMs }` 형태). 벤더 확정 전에는 어댑터 패턴으로 설계해 나중에 벤더만 바꿔도 파이프라인 나머지는 안 건드리게 한다.

---

### 7. 렌더링 위치 — 로컬 vs Remotion Lambda
**확정**: 1차는 로컬 렌더. 편수가 적고 해상도 부담이 크지 않은 초기 단계에서는 AWS 계정 설정·Lambda 배포 비용을 들일 이유가 없음.

**전환 조건(2차 트리거)**: 편당 렌더 시간이 반복 제작을 방해할 정도로 길어지거나, 동시에 여러 편을 렌더해야 할 때.

**Claude Code 구현 영향**: 렌더 스크립트는 `remotion render` CLI 직접 호출로 구현. Lambda 관련 설정(AWS 자격증명, `remotion lambda` 패키지)은 1차 구현에 포함하지 않는다.

---

### 8. 배포 자동화 — 수동 vs API 자동화
**확정**: 1차는 수동 업로드. 프로젝트 지침상 이 트랙은 배포 성과보다 파이프라인 학습이 우선이며, 초기 편수가 적을 때 API 자동화(OAuth 설정, 채널 연동)에 시간을 쓰는 것은 우선순위에 안 맞음.

**Claude Code 구현 영향**: 렌더링 산출물(mp4)과 메타데이터 초안(제목/설명/해시태그 텍스트 파일)까지가 파이프라인의 출력 범위. 업로드 API 연동은 구현하지 않는다.

---

### 9. 레포/프로젝트 구조 — 모노레포 vs 편당 별도 레포
| 옵션 | 장점 | 단점 |
|---|---|---|
| 모노레포 (공용 `remotion/` + `projects/편별폴더`) | 컴포넌트 재사용 쉬움, 설정 한 번만 관리 | 편이 많아지면 레포가 커짐 |
| 편당 별도 레포 | 완전히 독립적 | 공용 컴포넌트 중복, 설정 반복 |

**확정**: 모노레포. 1차 설계 문서의 폴더 구조(4장) 그대로 유지.

**Claude Code 구현 영향**: `npx create-video@latest`로 `remotion/` 초기화 후, `projects/`, `templates/`, `docs/`는 그 옆에 나란히 생성한다(별도 레포 분리 없음).

---

### 10. 데이터 스키마 — 단일 `script.json` vs 씬별 파일 분리
**확정**: 편당 단일 `script.json`. 씬 수가 적은 쇼츠 특성상 파일을 쪼갤 이유가 없고, 하나의 파일로 관리해야 ②→③→④ 단계 간 데이터 전달(특히 duration 역주입)이 단순해진다.

**Claude Code 구현 영향**: `templates/script_schema.json`을 기준 스키마로 두고, 편별 `script.json`은 이 스키마를 따르는지 간단히 검증(JSON Schema validation)하는 유틸을 만들어두면 이후 편 제작이 안정적이다.

---

### 11. 컴포넌트 재사용 전략 — 공용 라이브러리 vs 편별 커스텀
**확정**: 씬 타입별 공용 컴포넌트 라이브러리(`TitleScene`, `TalkingPointScene`, `CodeScene`, `OutroScene` 등). 프로젝트 지침상 "최소한의 일관된 포맷" 확보가 완성 기준 중 하나이므로, 컴포넌트를 공용화해야 편마다 톤이 흔들리지 않는다.

**Claude Code 구현 영향**: `remotion/src/components/scenes/`에 씬 타입별 컴포넌트를 두고, `script.json`의 `scene.type` 값으로 컴포넌트를 매핑하는 레지스트리(`sceneRegistry.ts` 등)를 구현.

---

### 12. 스크립트 생성 자동화 수준 — 반자동 vs 완전 자동  **[오픈]**
1차 설계 문서에서는 "Claude가 대본을 생성"이라고만 되어 있고, 이걸 어떤 방식으로 실행할지는 정해지지 않았다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| 반자동 (Claude Code 세션에서 사람이 매번 트리거) | 구현 간단, 소재별 품질 컨트롤 쉬움 | 완전 자동화는 아님 |
| 완전 자동 (Claude API를 파이프라인 스크립트에서 직접 호출) | 엔드투엔드 자동화 | API 키 관리, 프롬프트 템플릿 고도화 필요, 품질 편차 위험 |

**미확인 시 기본값**: 반자동. 편당 소재 선정(①단계)이 애초에 사람이 개입하는 지점으로 확정돼 있으므로, 대본 생성(②단계)도 같은 세션에서 자연스럽게 이어가는 것이 1차 구현 범위에 맞는다. 완전 자동화는 편수가 쌓인 뒤 검토.

**Claude Code 구현 영향**: 별도의 Claude API 연동 코드를 1차 구현에 넣지 않는다. 대신 `templates/`에 대본 생성용 프롬프트 템플릿을 문서화해 매 편 재사용한다.

---

### 13. 스캐폴딩 도구 — `create-video` vs 수동 Remotion 셋업
**확정**: `npx create-video@latest`. Remotion 공식 스캐폴딩 도구로, TypeScript 템플릿과 기본 구조를 바로 제공해 수동 셋업 대비 시간을 아낀다.

**Claude Code 구현 영향**: 첫 구현 커맨드는 `npx create-video@latest`(TypeScript 템플릿 선택) → `remotion/`으로 이동/리네임 → 1차 설계 문서의 폴더 구조에 맞게 `projects/`, `templates/`, `docs/` 추가.

---

### 14. TTS 발음 사전 (Pronunciation Lexicon) — **확정 규칙 (2026-08-16 사용자 지시)**

**배경**: 002 v2 렌더에서 TTS가 "JSON"을 "제이에스온"으로 읽는 문제 확인. 한국어 나레이션에서 영문 기술용어의 관용 발음을 보장해야 한다.

**규칙**:
- TTS에 넘기는 나레이션 텍스트에는 발음 치환을 적용한다. **자막·화면 표시 텍스트는 원문 표기("JSON")를 유지**한다 — 치환은 오디오 생성 입력에만 적용.
- 발음 사전은 `templates/tts_lexicon.json`으로 파일화하고, `generate-narration` 단계에서 TTS 호출 직전에 적용한다.
- 확정 항목: `"JSON" → "제이슨"`.
- 새 용어에서 오발음이 발견되면 이 사전에 항목을 추가하는 것을 표준 대응으로 한다.
- TTS 벤더가 SSML `<phoneme>`/`<sub>`를 지원하면 텍스트 치환 대신 SSML 방식으로 전환 가능하되, 사전 파일을 단일 소스로 유지한다.

**Claude Code 구현 영향**: `script.json`의 `narration` 필드는 원문 유지. 치환은 파이프라인 ③단계(TTS 생성) 내부에서만 수행.

### 15. 화면 캡처 보안 규칙 — **확정 (2026-08-16 보안 사고 후, 예외 없음)**

**배경**: ffmpeg gdigrab 기술 검증 중 에이전트가 사용자 실제 데스크톱 전체를 캡처하는 사고 발생 (에이전트 실행 환경 = 격리 샌드박스가 아니라 사용자 라이브 데스크톱). 캡처에 민감 업무 정보(고객사명·프로젝트명 등)가 포함됨. 파일 2개 즉시 삭제 조치 완료.

**규칙 (에이전트는 예외 없이 준수)**:
1. **에이전트에 의한 화면/데스크톱/창 자동 캡처 전면 금지.** `ffmpeg gdigrab`(desktop이든 창 제목 지정이든), 스크린샷 API, 기타 화면 캡처 도구를 에이전트가 직접 실행하지 않는다. 창 제목 지정 방식도 대상 오지정·창 겹침으로 민감정보가 찍힐 수 있으므로 금지에 포함.
2. **터미널 컷은 cast-builder 방식으로 생성** (화면 캡처 불필요): 실제 명령을 비대화형으로 실행해 stdout/stderr 캡처(TTY 불필요) → 빌더 스크립트가 실제 출력에 합성 타이밍을 입혀 `.cast` 호환 JSON 생성 → Remotion `TerminalScene`이 재생. 실물감은 실제 출력 내용에서, 타이밍은 연출 값. ANSI 컬러는 `--color=always`, TTY 필수 CLI는 winpty 경유 시도.
3. **GUI 컷(Remotion Studio, VS Code 등)은 사람이 수동 녹화**: Windows Game Bar(Win+Alt+R)는 활성 창만 녹화하므로 데스크톱 노출 위험이 구조적으로 차단됨. 사용자가 직접 녹화해 `projects/<편>/assets/captures/`에 투입하고, 에이전트는 투입된 파일만 소비한다.
4. **투입된 캡처는 편집 전 사람이 민감정보 육안 검수**를 거친다. 에이전트는 캡처 파일을 외부로 전송하지 않는다.

**Claude Code 구현 영향**: 캡처 자동화 코드를 파이프라인에 넣지 않는다. 파이프라인의 캡처 관련 책임은 (a) cast-builder 스크립트, (b) `assets/captures/` 폴더의 파일 존재 확인과 소비까지다.

## Claude Code 작업 순서 제안 (이 문서 기준)

1. `remotion/` 스캐폴딩 (`npx create-video@latest`)
2. `templates/script_schema.json` 작성 — 1차 설계 문서 3장 스키마 반영
3. TTS 어댑터 인터페이스 구현 (`ttsProvider.generate(text) → {audioPath, durationMs}`) — 발음 사전(`templates/tts_lexicon.json`) 적용 포함(항목 14)
4. 씬 컴포넌트 라이브러리 스캐폴딩 (`TitleScene`, `TalkingPointScene`, `CodeScene`, `OutroScene`) + `sceneRegistry.ts`
5. cast-builder 스크립트 + `TerminalScene` `.cast` 재생 (항목 15 규칙 준수)
6. 렌더 스크립트: `script.json` → duration 역주입 → `remotion render`
7. `projects/001_.../` 샘플 편 하나로 엔드투엔드 실행 검증

**시작 전 사용자에게 확인할 것**: 항목 6(TTS 벤더), 항목 12(스크립트 생성 자동화 수준). 나머지는 확정 상태로 바로 진행 가능.
